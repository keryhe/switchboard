## Phase 0 Spike Results (2026-07-26)

The Connector Mechanism Spike ([plans/phase-0-connector-mechanism-spike.md](../../plans/phase-0-connector-mechanism-spike.md)) ran against .NET 10 (`10.0.201`, shared framework `10.0.5`). Both unproven mechanisms are confirmed working with **no fallback needed** for either workstream. Full detail in [spike/findings/](../../spike/findings/).

- **Negotiate interception (Workstream A):** `NegotiateMetadata`, `MatcherPolicy`, `IEndpointSelectorPolicy`, and `CandidateSet.ReplaceEndpoint` all exist, are public, and match the design doc's assumed signatures exactly. `MapHub<T>()` confirmed (via a live endpoint dump) to attach `NegotiateMetadata` to the negotiate endpoint and to copy hub-class attributes (`[Authorize]`) onto both the negotiate and transport endpoints. 22 automated tests pass, including a real out-of-process `Microsoft.AspNetCore.SignalR.Client` connection and an unmodified `@microsoft/signalr` client, both reaching `Connected` purely via the registered policy, with `[Authorize]` on `SecureHub` still enforced (401 without a token, redirected with one). See [spike/findings/api-recon.md](../../spike/findings/api-recon.md).
- **Inbound dispatch (Workstream B):** `ConnectionBuilder`/`UseConnectionHandler<HubConnectionHandler<THub>>()`, `HandshakeProtocol.WriteRequestMessage`, and `ConnectionItems` all match the design doc's sketches. A hub method executes from raw bytes with no client attached, identity flows correctly through `IConnectionUserFeature`, the Completion/`Clients.All` return-path split holds, and lifecycle/rejection behave as expected within bounded timeouts. See [spike/findings/required-connection-features.md](../../spike/findings/required-connection-features.md).
- **Two corrections found by tests that actually exercised the design doc's claims** (not by static review) — both are proposed as doc corrections to [04-design.md §11](04-design.md#11-connector--inbound-dispatch-synthetic-client-connections), detailed in [spike/findings/inbound-dispatch-corrections.md](../../spike/findings/inbound-dispatch-corrections.md):
  1. The identity-reconstruction sketch's unconditional `authenticationType: "Switchboard"` would silently authenticate anonymous connections (`ClaimsIdentity.IsAuthenticated` depends only on a non-null `authenticationType`, not on claim count). Fixed: `authenticationType` is now conditional on `userId` being present.
  2. The rejection-path close frame in .NET 10 is `{"type":7,"error":"..."}` with **no `allowReconnect` field at all** — not `allowReconnect: false` as the design doc's sketch showed. Client libraries default a missing field to `false`, so behavior is unaffected, but the wire shape differs from what's documented.
- **One addition to the required-feature list:** `IConnectionLifetimeFeature` and `IConnectionCompleteFeature` are needed on the synthetic `ConnectionContext` alongside the four the design doc lists (`IConnectionUserFeature`, `IConnectionIdFeature`, `IConnectionItemsFeature`, `IConnectionHeartbeatFeature`). None of the original four turned out to be unnecessary.
- **One real bug found and fixed during host scaffolding, unrelated to the mechanisms themselves:** a minimal-API route (`/api/ping`) and an MVC controller route (`api/Ping`) collided under ASP.NET Core's case-insensitive route matching, producing an `AmbiguousMatchException`. Fixed by renaming the controller route; recorded here only because it's the kind of mistake worth watching for when Phase 1 adds routes alongside the Connector's policy.

**Carried into Phase 1** (per the spike plan's promotion boundary): `Phase0.Spike.Connector/Negotiate/SwitchboardNegotiateMatcherPolicy.cs` and `Phase0.Spike.Connector/Dispatch/*` (the synthetic `ConnectionContext`, `HubPipelineFactory`, `HandshakeWriter`, `IdentityReconstruction` — with the fix above already applied), plus the test clients. **Discarded:** `Phase0.Spike.Host` (throwaway host, stub redirect target, hardcoded JWT signing key, test hubs).

## Resolved 2026-07-26

**Connector inbound dispatch — designed ([04-design.md §11](04-design.md#11-connector--inbound-dispatch-synthetic-client-connections)).** The docs specified how the Connector *diverts* negotiate (§8) but never how an inbound `client_message` becomes a Hub method call. `IHubLifetimeManager` is outbound-only; everything inbound (`OnConnectedAsync`, argument binding, hub filters, per-method `[Authorize]`, streaming) lives in `HubConnectionHandler` → `DefaultHubDispatcher` and is unreachable without a `ConnectionContext`. Resolved with the mechanism the Azure SignalR SDK uses ([azure-signalr#13](https://github.com/Azure/azure-signalr/issues/13)): build a `ConnectionDelegate` via `ConnectionBuilder.UseConnectionHandler<HubConnectionHandler<THub>>()` and invoke it with a synthetic `ConnectionContext` backed by a `Pipe` pair. Decisions taken: `open_connection` carries `hubProtocol` (existing `[Key(5)]` field — no wire change) so the Connector can synthesize the mandatory handshake; identity is trusted from the envelope and attached via `IConnectionUserFeature`; rejection reuses `close_connection` with `error` rather than adding an ack round-trip. Applied to [03-protocol.md §2.3](03-protocol.md#23-message-envelope-format), [05-data-models.md](05-data-models.md), and [06-project-plan.md](06-project-plan.md) Phases 0–1.

**Class-level `[Authorize]` had a silent-drop hole — fixed in [04-design.md §8](04-design.md).** Verification against upstream source found that `MapHub<THub>()` copies hub-type attributes into *endpoint metadata*, so class-level `[Authorize]` is enforced by `AuthorizationMiddleware` on the HTTP request, while `DefaultHubDispatcher` enforces only *per-method* authorization and does no class-level check on connect. Because the client's transport request terminates at Switchboard and never reaches the app server, negotiate is the **only** surviving enforcement point — so a `MatcherPolicy` that swaps in a bare endpoint drops hub authorization with no error (the sample's `[Authorize] ChatHub` depends on it). §8 now requires the replacement endpoint to be built from the original's `Metadata`, and Phase 0 asserts it directly. (Sources: [HubEndpointRouteBuilderExtensions.cs](https://github.com/dotnet/aspnetcore/blob/main/src/SignalR/server/SignalR/src/HubEndpointRouteBuilderExtensions.cs), [DefaultHubDispatcher.cs](https://github.com/dotnet/aspnetcore/blob/main/src/SignalR/server/Core/src/Internal/DefaultHubDispatcher.cs).)

**`Context.UserIdentifier` vs. the service's user index — reconciled.** `UserIdentifier` is computed by `IUserIdProvider` (default: `ClaimTypes.NameIdentifier`), while the service routes `send_to_user` on the `userId` captured at negotiate; divergence would break `Clients.User(...)` silently. The Connector now synthesizes `NameIdentifier` from the envelope `userId`. A custom `IUserIdProvider` remains a documented hazard (risk register) that must be mirrored in the app server's forwarded negotiate.

**Phase 0 spike scope widened.** Previously covered negotiate interception only. It now also proves inbound dispatch — the other unproven Connector mechanism — plus the `[Authorize]` metadata assertion. Renamed *Connector Mechanism Spike*.

### Medium — resolved

**Management API auth — decided: a separate management token.** [ADR-004](07-adr/ADR-004-token-authority.md)'s position wins over the "server access token **or** …" alternative that [03-protocol.md Part 3](03-protocol.md#part-3-management-rest-api) previously allowed: an app server token must not be able to drive the management API. Part 3 now specifies the management token's required claims (`role: management`, `aud` = `ManagementAudience`) and its CLI generation; `ManagementSigningKey` / `ManagementSigningKeyFallback` / `ManagementAudience` added to `SwitchboardOptions` ([05-data-models.md](05-data-models.md)); `GET /api/v1/health` corrected from "server or management token" to management only; ADR-004 gained a three-token summary table; Phase 4 deliverable updated.

**Pattern A — specified, and its flow corrected.** Writing it up exposed a latent contradiction: a *non-redirect* negotiate response has no field able to carry an access token, so Pattern A as drafted could not authenticate its own transport upgrade. Resolved by having service-direct negotiate **return a redirect to itself**, reusing Pattern B's entire token-issuance and Accept-Phase path rather than introducing a second transport-auth mode with `connectionToken` as a bearer secret. Identity comes from `X-Switchboard-UserId` / `X-Switchboard-Claims`, governed by four mandatory security rules (disabled by default; fail-fast startup when enabled with an empty allowlist; headers stripped for non-allowlisted peers; match on the immediate peer, not `X-Forwarded-For`). Config added to `SwitchboardOptions`; implementation is a **Phase 2** deliverable (config + header handling), deliberately kept out of Phase 1 so the MVP milestone stays focused on the Pattern B end-to-end flow.

**Backpressure default — decided: `DropWrite`.** `WriteChannelFullMode` default flipped from `BoundedChannelFullMode.Wait`, which contradicted the non-blocking fan-out described in [02-architecture.md](02-architecture.md) and [04-design.md §5](04-design.md). A slow client now sheds messages instead of stalling broadcast fan-out for every other client.

**Phase 3 group membership — clarified.** `IGroupGrain` is the single source of truth under clustering; `InMemoryConnectionRegistry` is not in play (`OrleansConnectionRegistry` replaces it wholesale, per [ADR-002](07-adr/ADR-002-connection-registry.md)). The per-node `connectionId → groupNames` map is a **node-local cache** living beside the transport handles in `ILocalTransportRegistry`, used only to avoid a cross-grain scan on disconnect — never for routing or membership queries.

The two names are distinct and both are correct in their own place: `AddSwitchboard()` registers the **service** ([05-data-models.md](05-data-models.md) Service Registration Summary), `AddSwitchboardConnector()` registers the **connector** on an app server.

## Already resolved (2026-07-12)

**Negotiate interception mechanism.** The original `AddSingleton<NegotiateHandler, …>()` DI-override approach was verified against the ASP.NET Core framework source and the Azure SignalR SDK and found to be a no-op — the framework processes negotiate inline in `HttpConnectionDispatcher` and resolves no `NegotiateHandler` service. [04-design.md §8](04-design.md) and [06-project-plan.md](06-project-plan.md) Phase 1 now use the supported endpoint-routing `MatcherPolicy` seam (`SwitchboardNegotiateMatcherPolicy` implementing `MatcherPolicy` + `IEndpointSelectorPolicy`, targeting `NegotiateMetadata` endpoints), which is the same mechanism Azure SignalR's `NegotiateMatcherPolicy` uses. (Sources: [HttpConnectionDispatcher](https://github.com/dotnet/aspnetcore/blob/main/src/SignalR/common/Http.Connections/src/Internal/HttpConnectionDispatcher.cs), [Azure SignalR internals](https://learn.microsoft.com/en-us/azure/azure-signalr/signalr-concept-internals).)

**Redirect / second-negotiate chain.** [03-protocol.md §1.1–1.2](03-protocol.md) and [08-sample-app.md](08-sample-app.md) now document the standard two-step SignalR redirect flow: step 1 returns a redirect response (`url` + `accessToken` only, `url` is `https://` not `wss://`); the client re-negotiates at the service `url` in step 2 to obtain `connectionId` / `connectionToken` / `availableTransports`; transports then connect with `id={connectionToken}`. Fixed the `wss://` → `https://` redirect URL and switched all transport `id` params to `connectionToken` throughout. Residual `connectionToken`-vs-`connectionId` value decision tracked under Medium above. (Source: [Azure SignalR internals](https://learn.microsoft.com/en-us/azure/azure-signalr/signalr-concept-internals).)

**`connectionToken` vs `connectionId` — decided: distinct.** `connectionId` is the public identity (hub code, `send_to_connection`, groups, management API); `connectionToken` is an opaque, unguessable handle minted at the step-2 negotiate, used only as the transport `id`, and never exposed by the management API. In Phase 3 the token encodes the owning node for routing. Applied to [03-protocol.md §1.1](03-protocol.md) (resolved the note), [05-data-models.md](05-data-models.md) (added `ConnectionToken` to `ClientConnectionState` + note), and [04-design.md §2](04-design.md) (accept-phase resolves the token at transport upgrade). Matches Azure SignalR and standard SignalR v1 semantics.

**Minor cleanup.** Fixed the [08-sample-app.md](08-sample-app.md) `AddAuthorize()` → `AddAuthorization()` typo. Split `/healthz` ([03-protocol.md](03-protocol.md)) into a public, unauthenticated liveness/readiness probe (200/503, `{ "status": "healthy" }`, no counts or hub names) and an authenticated `GET /api/v1/health` behind the management API that returns the per-hub connection detail; [06-project-plan.md](06-project-plan.md) Phase 4 updated to match.

**Stateful reconnect — decided: deferred / not supported.** Keeps fire-and-forget as a non-goal. Stateful reconnect (`.withStatefulReconnect()`, .NET 8+) buffers un-acked messages for replay on resume — the replay the overview already excludes, and costly in a proxy/clustered topology (per-connection buffers; owner-node-bound state). Because it's a negotiated opt-in feature, clients that request it fall back to standard reconnect, so this is not a compatibility break. Updated [ADR-005](07-adr/ADR-005-protocol-compatibility.md) (compatibility table row → "Not supported"; added a "not in scope" entry; softened the future-proofing bullet) and [01-overview.md](01-overview.md) Non-Goals (explicit stateful-reconnect note). Listed as a candidate future enhancement.

**Server-facing envelope format — decided: binary MessagePack.** The app server ↔ service protocol (handshake + all envelopes) is a single MessagePack, length-prefixed format; `payload` carries the inner hub message as raw bytes (MessagePack `bin`), never base64. Chosen over always-JSON (which imposes ~33% base64 inflation, worst for MessagePack clients) and over a JSON-now/MessagePack-later split; matches the Azure SignalR server-service protocol and the `byte[] Payload` the model already used. Applied to [03-protocol.md Part 2](03-protocol.md) (wire-format note + §2.2/§2.3 reframed, base64 annotations removed), [05-data-models.md](05-data-models.md) (`ServerEnvelope` now `[MessagePackObject]` / `[Key(n)]`, payload = raw bytes), and [06-project-plan.md](06-project-plan.md) Phase 1 (envelope is MessagePack; JSON `\x1e` framing is now scoped to the client-facing hub protocol). MessagePack was already a `Keryhe.Switchboard.Protocol` dependency, so no new package.

**Server-token transport on forwarded negotiate — decided: `Authorization: Bearer`.** The app server presents the server access token as `Authorization: Bearer <server token>` on the forwarded negotiate, matching the WebSocket-connection ([03-protocol.md §2.1](03-protocol.md)) and management-API ([03-protocol.md Part 3](03-protocol.md)) uses of the same token. The pre-validated user identity continues to travel in `X-Switchboard-UserId` / `X-Switchboard-Claims`. Fixed the sample ([08-sample-app.md](08-sample-app.md)) to drop the custom `X-Switchboard-ServerToken` header; [04-design.md §8](04-design.md) was already canonical.

**Client JWT claim names — decided: domain claims.** The client access token uses `connectionId` and `hubName` (custom claims) + `sub` (standard, userId); dropped the `jti` overload and the `nameid` alternative. Rationale: the token is private to this service and opaque to SignalR clients (no wire constraint), so domain-matching names win over overloading `jti` with the connection's public identity. Applied to [04-design.md §1](04-design.md) (claims block + a "private token" note), [05-data-models.md](05-data-models.md) (`ConnectionId` comment), [03-protocol.md §1.1](03-protocol.md) (`sub` only), and [02-architecture.md](02-architecture.md) (JWT Token Authority claims list). The **server** access token ([03-protocol.md §2.1](03-protocol.md): `sub`/`role`/`hubs`/…) is a separate, already-consistent token and was not touched.

**Two-step negotiate shape propagated.** Reconciled every doc that still showed the old single-hop negotiate response to the two-step redirect + `connectionToken` model: [04-design.md §1](04-design.md) (`INegotiationService` split into `IssueRedirectAsync` → `RedirectResponse` and `NegotiateAsync` → `NegotiateResponse`; Pattern A/B flows), [04-design.md §8](04-design.md) (redirect handler now receives `{url, accessToken}` only), [05-data-models.md](05-data-models.md) (`RedirectResponse` + `NegotiateResponse` models), and [02-architecture.md](02-architecture.md) (Negotiation API I/O description + Data Flow Diagram #1 now shows the step-2 re-negotiate). This completes the redirect-chain propagation.

**Backplane naming.** Reconciled all docs to the final Grain-Observers backplane design (ADR-003 / [04-design.md §7](04-design.md)):
README.md, 01-overview.md, 02-architecture.md, 05-data-models.md, 06-project-plan.md, ADR-002. Removed stray `IServiceNodeGrain` / Orleans Streams / Redis references that predated the design's final iteration.
