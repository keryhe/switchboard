## Phase 0 Spike Results (2026-07-26)

The Connector Mechanism Spike ([plans/phase-0-connector-mechanism-spike.md](../../plans/phase-0-connector-mechanism-spike.md)) ran against .NET 10 (`10.0.201`, shared framework `10.0.5`). Both unproven mechanisms are confirmed working with **no fallback needed** for either workstream. Full detail in [docs/docs/09-phase0-findings/](09-phase0-findings/).

- **Negotiate interception (Workstream A):** `NegotiateMetadata`, `MatcherPolicy`, `IEndpointSelectorPolicy`, and `CandidateSet.ReplaceEndpoint` all exist, are public, and match the design doc's assumed signatures exactly. `MapHub<T>()` confirmed (via a live endpoint dump) to attach `NegotiateMetadata` to the negotiate endpoint and to copy hub-class attributes (`[Authorize]`) onto both the negotiate and transport endpoints. 22 automated tests pass, including a real out-of-process `Microsoft.AspNetCore.SignalR.Client` connection and an unmodified `@microsoft/signalr` client, both reaching `Connected` purely via the registered policy, with `[Authorize]` on `SecureHub` still enforced (401 without a token, redirected with one). See [09-phase0-findings/api-recon.md](09-phase0-findings/api-recon.md).
- **Inbound dispatch (Workstream B):** `ConnectionBuilder`/`UseConnectionHandler<HubConnectionHandler<THub>>()`, `HandshakeProtocol.WriteRequestMessage`, and `ConnectionItems` all match the design doc's sketches. A hub method executes from raw bytes with no client attached, identity flows correctly through `IConnectionUserFeature`, the Completion/`Clients.All` return-path split holds, and lifecycle/rejection behave as expected within bounded timeouts. See [09-phase0-findings/required-connection-features.md](09-phase0-findings/required-connection-features.md).
- **Two corrections found by tests that actually exercised the design doc's claims** (not by static review) — both are proposed as doc corrections to [04-design.md §11](04-design.md#11-connector--inbound-dispatch-synthetic-client-connections), detailed in [09-phase0-findings/inbound-dispatch-corrections.md](09-phase0-findings/inbound-dispatch-corrections.md):
  1. The identity-reconstruction sketch's unconditional `authenticationType: "Switchboard"` would silently authenticate anonymous connections (`ClaimsIdentity.IsAuthenticated` depends only on a non-null `authenticationType`, not on claim count). Fixed: `authenticationType` is now conditional on `userId` being present.
  2. The rejection-path close frame in .NET 10 is `{"type":7,"error":"..."}` with **no `allowReconnect` field at all** — not `allowReconnect: false` as the design doc's sketch showed. Client libraries default a missing field to `false`, so behavior is unaffected, but the wire shape differs from what's documented.
- **One addition to the required-feature list:** `IConnectionLifetimeFeature` and `IConnectionCompleteFeature` are needed on the synthetic `ConnectionContext` alongside the four the design doc lists (`IConnectionUserFeature`, `IConnectionIdFeature`, `IConnectionItemsFeature`, `IConnectionHeartbeatFeature`). None of the original four turned out to be unnecessary.
- **One real bug found and fixed during host scaffolding, unrelated to the mechanisms themselves:** a minimal-API route (`/api/ping`) and an MVC controller route (`api/Ping`) collided under ASP.NET Core's case-insensitive route matching, producing an `AmbiguousMatchException`. Fixed by renaming the controller route; recorded here only because it's the kind of mistake worth watching for when Phase 1 adds routes alongside the Connector's policy.

**Carried into Phase 1** (per the spike plan's promotion boundary): `Phase0.Spike.Connector/Negotiate/SwitchboardNegotiateMatcherPolicy.cs` and `Phase0.Spike.Connector/Dispatch/*` (the synthetic `ConnectionContext`, `HubPipelineFactory`, `HandshakeWriter`, `IdentityReconstruction` — with the fix above already applied), plus the test clients. **Discarded:** `Phase0.Spike.Host` (throwaway host, stub redirect target, hardcoded JWT signing key, test hubs).

## Phase 1 Core Service (MVP) Results — implemented, milestone green (2026-07-26)

All six slices from [plans/phase-1-core-service-mvp.md](../../plans/phase-1-core-service-mvp.md) are implemented against .NET 10 (`10.0.201`): scaffolding, protocol primitives, negotiate/JWT/registries, the server-facing WebSocket connection, the client-facing WebSocket transport + router, and the Connector (promoted from the spike, with real negotiate forwarding and real inbound dispatch). 31 unit tests pass covering the mechanism at every layer.

- **Two framework facts verified during implementation, beyond what the plan already recorded:**
  1. `Microsoft.AspNetCore.SignalR.IInvocationBinder` lives in that exact namespace (not `.Protocol`), in `Microsoft.AspNetCore.SignalR.Common.dll` — needed by the Connector's outbound pipe reader to parse `HubConnectionHandler`'s own output messages.
  2. `EndpointDataSource` resolved via DI is **not** guaranteed populated by the time `IHostedService.StartAsync` runs, even after `MapHub<T>()` has been called — hosted-service start order is registration order, not "routing is definitely built first." The Connector's hub-discovery hosted service (plan decision D2) had to move its discovery logic into an `IHostApplicationLifetime.ApplicationStarted` callback instead, which is the first point every mapped hub is guaranteed visible.
  3. Hub names for the service's own routes (`/{hub}/negotiate`, `/{hub}`, `/server/{hub}`) must be a **single path segment** — ASP.NET Core's `{hub}` route parameter does not span multiple segments. The illustrative `/api/chatHub` path in [08-sample-app.md](08-sample-app.md) doesn't satisfy this; `SampleChatApp.Api` maps `ChatHub` at `/chatHub` instead. Worth a doc correction if Phase 2 revisits that illustration.
- **One MessagePack wire-contract addition:** `ServerEnvelope` gained a `Version` field at the next free key (`[Key(10)]`) to carry the handshake protocol version (§2.2) — the original `[Key(0..9)]` layout in [05-data-models.md](05-data-models.md) had no field for it. Additive only; existing keys unchanged.
- **Resolved: the inbound-dispatch stall (`\x1e` stripped from `client_message` payloads).** A client-invoked hub method (`Echo`, `JoinRoom`, …) never dispatched when routed through the *real* Connector over a real network, with no exception on either side. **Root cause:** on the service side, `WebSocketClientTransport.ReadAllAsync` splits the client's WebSocket bytes into hub-protocol frames using `JsonFrameProtocol.TryParseFrame`, which — correctly, for a frame reader — yields each frame with the `\x1e` record separator **removed**. `ClientConnectionEndpoint` then handed that delimiter-stripped frame straight to `DefaultMessageRouter.RouteClientMessageAsync`, which copies it verbatim into the `client_message` envelope's `payload`. But the server-facing contract ([03-protocol.md §2.4](03-protocol.md), [04-design.md §11](04-design.md)) is that `payload` is raw hub-protocol bytes *including* framing, because the Connector writes it verbatim into the synthetic connection's pipe where `IHubProtocol.TryParseMessage` needs the delimiter to recognise a complete message. Undelimited, the bytes sat in the pipe unparsed forever — `HubConnectionHandler`'s dispatch loop was working correctly and simply never saw a complete message. The teardown symptom (`InvalidDataException: Connection terminated while reading a message.`) was the same undelimited remainder being reported when the pipe finally completed. **Why every isolated bisection passed:** `InboundDispatcherTests` builds its own payload with `JsonFrameProtocol.WriteFrame` (framed), and `ClientRouterEndToEndTests`' hand-rolled app-server double inspects the `client_message` envelope but never feeds it to a real hub pipeline — so neither exercises the one line that dropped the delimiter. The outbound direction was never affected because `IHubProtocol.WriteMessage` emits the delimiter itself. **Fix:** `ClientConnectionEndpoint` re-applies the record separator when constructing the `client_message` payload. `ConnectorEndToEndTests` (the minimal `Echo` repro) is the only test that covers this path end to end and is now unskipped and green.
- **Known Phase 1 gap surfaced by the milestone test (not a bug):** `ChatHub.SendMessage` fans out via `Clients.Group(roomId)`, and group fan-out is a deliberate log-and-no-op in Phase 1 (plan decision **D3**; real routing is Phase 2). `MilestoneEndToEndTests` was written asserting the group message comes back, which Phase 1 cannot satisfy — that assertion was masked by the `Skip`. It now asserts the *absence* of group delivery (per the plan's "assert absence, not just presence" guidance) with a message telling whoever lands Phase 2 to flip it into the positive assertion. Group *membership* tracking (`add_to_group` → `IConnectionRegistry`) already works; only fan-out is deferred.

## Phase 2 Slices 5-6 (SSE, Long Polling) Results (2026-07-27)

- **SSE finding: `HttpResponse.StartAsync()` alone does not push headers to the client.** A real `HubConnection` pinned to `HttpTransportType.ServerSentEvents` hung indefinitely at `StartAsync()` — its internal `ServerSentEventsTransport.StartAsync` sends the GET with `HttpCompletionOption.ResponseHeadersRead` and blocks until headers actually arrive over the wire, but the service's SSE GET handler had already sent them logically (`context.Response.StartAsync(ct)` ran, `OnStarting` callbacks fired, headers were locked) without an explicit flush ever putting bytes on the socket — Kestrel buffers the response until the first real write or an explicit flush. **Fix:** `SseClientEndpoint` calls `await context.Response.Body.FlushAsync(ct)` immediately after `StartAsync`. Found by decompiling the real client transport (`ilspycmd` against `Microsoft.AspNetCore.Http.Connections.Client.dll`) rather than guessing, once a raw `HttpClient`-driven repro (no `ResponseHeadersRead` completion option) worked fine and isolated the difference to header delivery timing.
- **Long Polling finding: a plain poll timeout must return `200` with an empty body, not `204`.** [03-protocol.md §1.6](03-protocol.md) originally read "200 with accumulated messages, or 204 No Content after timeout" — read literally, this would end the connection on every idle period, because the real client's `LongPollingTransport.Poll()` treats **any** `204` response as "the server says this connection is over" and stops polling for good (verified by decompiling both `Microsoft.AspNetCore.Http.Connections.Client.Internal.LongPollingTransport` and the real server-side `LongPollingServerTransport.ProcessRequestAsync` from the shared framework: the latter returns `200`/empty on its own poll-timeout token, and reserves `204` exclusively for when the underlying pipe reader has actually completed with nothing left to drain). Switchboard's implementation matches the verified real behavior, not the doc's original wording — `LongPollingClientTransport.PollAsync` distinguishes "timed out, nothing buffered" (→ `LongPollResult.Empty`, 200) from "`Output`'s writer completed and nothing was left" (→ `LongPollResult.ClosedResult`, 204). §1.6 has been corrected to describe this precisely.
- **Long Polling finding: the establishing GET returns immediately, with the connection's message loop detached from that request.** Real client's `LongPollingTransport.StartAsync` sends one GET and only checks for a success status — it never reads the body — before immediately starting its own repeated poll loop. The hub-protocol handshake itself arrives afterward, over the first POST. Since a `ClientConnection` requires a negotiated `hubProtocol` that doesn't exist yet at this point, the establishing GET only registers the bare `LongPollingClientTransport` (via `ClientConnectionManager.RegisterTransport`, the same mechanism SSE's Slice 5 needed) and kicks off a detached background task to run the handshake + message loop for the rest of the connection's life — unlike SSE, no single HTTP request stays open long enough to own that task directly.

## Phase 2 Slice 7 (Streaming, CancelInvocation, Send/SendCore) Results (2026-07-27)

A verification slice by design (plan decision **D12**) — the architecture already covers server→client streaming, client→server streaming, `CancelInvocation`, and `Send`/`SendCore` with no new mechanism, so the work was proving it end to end (real client, real Connector, both hub protocols, multiple transports) rather than building anything. It found exactly the one bug the plan predicted and no others: 10 new tests (`ConnectorEndToEndTests`) pass, covering server→client streaming over JSON/WebSocket and MessagePack/Long Polling, client→server streaming over Long Polling, `Send` with no invocation id, a client-cancelled stream (proven by the hub method's own `finally` signaling, not just the client stopping enumeration), and a faulting stream surfacing `HubException` in the `Completion`.

- **Confirmed and fixed: `InboundDispatcher`'s outbound reader was lossy for MessagePack (finding 7).** It parsed every outbound hub message with an `EmptyBinder` (`GetReturnType`/`GetStreamItemType` → `typeof(object)`) and then **re-serialized** the parsed `HubMessage` before forwarding it — for JSON this happens to survive by accident (the value round-trips through a `JsonElement`), but for MessagePack, arguments and stream items reconstructed from loosely-typed CLR objects do not reliably re-encode to the same bytes. **Fix:** the outbound reader now parses only to *classify* (drop the pipeline's own `Ping`, detect `Close`) and forwards the exact bytes `TryParseMessage` consumed — captured as `before.Slice(0, before.Length - buffer.Length)` before/after the parse call — never re-encoding. This is a prerequisite for correct MessagePack streaming, not a nicety: `ServerToClientStreaming_MessagePackOverLongPolling_DeliversAllItems_ThenCompletes` is the test that would have caught the old behavior if it were still lossy in a way that broke plain integers (it happened not to, for this particular payload shape, which is exactly the kind of accidental survival the plan warned about — the fix removes the risk rather than reacting to an observed failure).
- **No new mechanism needed.** `StreamInvocation`, `StreamItem`, `Completion`, `CancelInvocation`, and `Send`/`SendCore` all rode the existing `client_message`/`send_to_connection` envelope path unchanged, across WebSocket, SSE, and Long Polling alike, confirming D12's premise.

## Phase 2 Slice 8 (Pattern A Direct Negotiate) Results (2026-07-27)

Implements plan decision **D11**'s ordered dispatch in `NegotiateEndpoint.HandleAsync`: a valid server token trusts identity headers unconditionally (Pattern B — the trust boundary is the token, never the network); a valid client token proceeds to step 2 as always; only when neither validates does the network allowlist get consulted at all, and only when `EnableDirectNegotiate` is on. A peer outside `TrustedProxyNetworks` still gets a connection — an anonymous one, with the identity headers actually removed from the request (`DirectNegotiateIdentity.ExtractIdentity`), not merely left unread.

- **Framework choice: `System.Net.IPNetwork` (added .NET 8) does exactly what D11's CIDR matching needs** — `IPNetwork.TryParse("10.0.0.0/8", out var network)` + `network.Contains(peerAddress)` — so no hand-rolled CIDR parser was needed. `DirectNegotiateIdentity.IsTrustedPeer` normalizes an IPv4-mapped-IPv6 peer address (`::ffff:10.0.0.1`) via `MapToIPv4()` before matching, since a dual-stack listener can report loopback/IPv4 peers in that form.
- **Verified end to end, not just at the token layer:** `DirectNegotiateEndToEndTests` runs a real app server behind the real Connector and asks a real Hub method for `Context.User.Identity.IsAuthenticated`/`Context.UserIdentifier` — confirming the Phase 0 `IdentityReconstruction` fix (anonymous connections must not have `IsAuthenticated == true` merely because they have no claims) actually protects Pattern A's anonymous-fallback path, not just Pattern B. All four gate scenarios pass: allowlisted peer's identity reaches `Context.User`; a non-allowlisted peer asserting `X-Switchboard-UserId: admin` gets a real, anonymous connection (never a rejection — that's the point of rule 3, and it surprises people); Pattern B is provably unaffected by an allowlist that would exclude the same peer; `EnableDirectNegotiate = false` still 401s an untokened request. The existing fail-fast startup validation (`EnableDirectNegotiate` true with empty `TrustedProxyNetworks`) is now pinned by a test asserting `Program.BuildApp(...).StartAsync()` throws `OptionsValidationException`.

## Phase 2 Slice 9 (CORS, Angular Sample, Compatibility Matrix) Results (2026-07-27)

- **Real bug found by running the Angular sample in a live browser, not by any automated test: `SwitchboardOptions.ClientKeepAliveInterval` was declared but never wired to anything.** The service never sent a client a hub-level `Ping`, so any connection idle for longer than the real `HubConnection`'s default 30s `ServerTimeout` was torn down by the *client* as presumed-dead and silently reconnected — every prior end-to-end test in this project completes in well under a second, so this path was never exercised until a real browser session sat open. Symptom in the browser console: `Error: Server timeout elapsed without receiving a message from the server.` on a loop, roughly every 30s. **Fix:** `ClientConnectionLifecycle.RunAsync` now runs a periodic keep-alive `Ping` loop (`RunKeepAlivePingLoopAsync`), symmetric to `ServerConnectionEndpoint`'s existing server-connection ping loop, writing `ClientFrameWriter.Ping(connection.HubProtocol)` to the transport's `Output` every `ClientKeepAliveInterval` for the lifetime of the connection — across all three transports (WebSocket, SSE, Long Polling), since all three share this lifecycle method. Pinned by `ClientKeepAliveEndToEndTests` (a short 200ms interval / 1s `ServerTimeout` rather than waiting out the real 15s/30s defaults), verified to actually catch the regression by reverting the fix and confirming the test fails.
- **`Origin` is not covered by `app.UseCors` for a WebSocket upgrade, exactly as the plan predicted.** `ClientConnectionValidation.IsOriginAllowed` enforces `AllowedOrigins` explicitly in `ClientConnectionEndpoint` before any token validation — absent when `AllowedOrigins` is empty (matching CORS's own permissive-by-default posture) or when the request carries no `Origin` header at all (the .NET client and other non-browser callers never send one, so `AllowedOrigins` must not lock them out). CORS preflight on the ordinary HTTP endpoints (negotiate, and the SSE/Long Polling POST/DELETE routes) turned out to already work correctly via the existing global `app.UseCors("Switchboard")` default policy — verified rather than assumed, via `CorsAndOriginEndToEndTests`.
- **Route correction from Phase 1 confirmed again in a new context:** the Angular `ChatService` must connect to the API's real `/chatHub` route, not the illustrative `/api/chatHub` from [08-sample-app.md](08-sample-app.md) — the dev proxy forwards `/chatHub` (and separately `/api`) to `SampleChatApp.Api`, matching the single-path-segment `{hub}` constraint recorded in the Phase 1 results above.
- **`SampleChatApp.Angular` built and manually verified end to end in a real browser** against the real `Keryhe.Switchboard.Server` and `SampleChatApp.Api` (no mocks): login, join, cross-client group `SendMessage`/`ReceiveMessage` both directions, `UserJoined`/`UserLeft` on join/leave, and a server-initiated `SystemMessage` push via a new `RoomsController` demo endpoint driving `IHubContext<ChatHub>` — exercising every row of [08-sample-app.md](08-sample-app.md)'s "What This Sample Exercises" table.
- **The transport × protocol matrix** (`TransportProtocolMatrixEndToEndTests`) is a single parameterized theory over the five valid cells rather than five near-duplicate test methods, per the plan's "parameterize, don't duplicate" guidance; the impossible SSE+MessagePack cell is pinned with a negative assertion against a real negotiate response (`transferFormats` for `ServerSentEvents` contains `Text`, never `Binary`) rather than left as a silent gap.
- **`js-redirect-check` retargeted** at `SampleChatApp.Api`'s real `/chatHub` (logging in via its dev-only `/api/auth/login` first, since `ChatHub` is `[Authorize]`) and its assertion upgraded from the retired `__diag` stub-observation check to a real hub method round-trip (`JoinRoom` + `SendMessage` → `ReceiveMessage`), since reaching `Connected` alone can't catch a routing bug downstream of the redirect. Run live against real processes: both PASS lines confirmed.

## Phase 5 Compatibility Testing & Benchmarking Results (2026-08-02)

All six slices from [plans/phase-5-compatibility-testing-and-benchmarking.md](../../plans/phase-5-compatibility-testing-and-benchmarking.md) are implemented. 233 unit tests + 3 integration tests pass (the Phase 4 baseline plus six new Slice 3 tests — `KnownIncompatibilityTests`, `ClientResultsTests`, `HubLifetimeManagerCoverageTests`), plus 21 tests in the new `Keryhe.Switchboard.CompatibilityTests` project. Phase 5 was explicitly the first **validation** phase rather than a construction phase, and its own charter — "surface real defects, don't produce vacuous green" — held: it found and fixed a real, 100%-reproducible bug before a single slice shipped (finding 1, below), and surfaced four more along the way.

- **Slice 1 (the .NET 8 row, and the SSE bug it found) — the single most important result of this phase.** A real `net8.0` `HubConnection` pinned to `HttpTransportType.ServerSentEvents` failed `StartAsync` 100% of the time against the unpatched service with `FormatException: Unexpected '\n' in message` — [SseClientEndpoint.cs](../../src/Keryhe.Switchboard.Server/ClientConnections/SseClientEndpoint.cs)'s `WriteOutputAsync` terminated every SSE event with a bare `"\n\n"`; the .NET 8 client's SSE parser requires `"\r\n\r\n"`, the .NET 10 client's does not. **Every one of the 227 tests passing at the end of Phase 4 drove a .NET 10 client** — a correctly-parameterized transport × protocol matrix that never varies the SDK cannot find an SDK-specific defect by construction (plan decision D30's entire argument). Reproduced deliberately before fixing: reverted the fix, reran the SSE cell, watched it fail with the exact reported exception, then restored the fix and reran — the same discipline this project has used since Phase 1, applied here to a bug found *before* the phase's slices were written rather than by them. Fixed with a two-character change (`"\n\n"` → `"\r\n\r\n"`); [03-protocol.md §1.5](03-protocol.md) corrected to specify CRLF. Also unblocked in the same slice: `SampleChatApp.Api` was missing `.AddMessagePackProtocol()` (finding 3) — without it, `HubConnectionHandler`'s `IHubProtocolResolver` rejects every MessagePack client outright, so no MessagePack cell against the real sample app was testable at all until this one-line fix landed; it also unblocked the real Connector + MessagePack + out-of-process combination (finding 4), which — despite MessagePack being covered thoroughly elsewhere — had never actually been exercised together before this slice. The probe contract (D30: one written scenario — connect, receive a caller push, join a group, invoke, receive the group message, disconnect — every SDK probe implements identically) and `ProbeRunner` (spawns a probe process, parses its `RESULT OK/FAIL` line, mirrors `ProcessFixture`'s own spawn shape) both landed here as the reusable foundation for Slice 2.
- **Slice 2 (JavaScript and Java rows)** — JS probes for **both** `@microsoft/signalr` 8.0.17 and 10.0.0 (finding 9: the SDK-version argument from finding 1 applies just as much to JS as to .NET), each with `@microsoft/signalr-protocol-msgpack` added for the MessagePack cells (finding 10, a separate npm package `SampleChatApp.Angular` didn't reference either). All 10 JS cells (2 versions × 5 valid transport/protocol combinations) pass. Two real bugs found and fixed while building the JS probe, both worth remembering for any future probe: MessagePack payloads deserialize with **PascalCase** field names client-side (no camelCase policy applied, unlike the JSON hub protocol, since MessagePack's contractless resolver doesn't apply one) — a probe that only checks `message.text` silently reads `undefined` over MessagePack; and an open WebSocket/long-polling handle keeps a Node process alive even after its `RESULT` line is printed, so without an explicit `process.exit()` at the very end, `ProbeRunner`'s process-exit wait times out on a cell that actually diagnosed correctly. `js-redirect-check` retired — nothing ran it automatically (finding 9), and its negotiate-redirect assertion is a strict subset of the probe scenario. The Java row (`com.microsoft.signalr` 9.0.6, Docker-gated per **D34**, reusing the `PostgresContainerFixture`/`OtlpCollectorContainerFixture` throwaway-container pattern) surfaced two real SDK limitations found by inspecting the actual jar rather than assumed: `TransportEnum` has no `SERVER_SENT_EVENTS` member at all (only `WEBSOCKETS`/`LONG_POLLING`/`ALL`), and the jar ships no MessagePack hub protocol class whatsoever. A third, found only empirically while writing the Java compatibility tests: this SDK version's `LongPollingTransport` never attaches the access token to its establishing GET request (confirmed via the service's own request log — a 401 on the very first GET, with `Authorization` header set and `accessTokenProvider` configured identically to the working `WEBSOCKETS` cell), so Switchboard correctly rejects it. Given this project's actual usage is .NET/JS-centric, this is recorded as a documented SDK limitation rather than chased into the library's internals — the one cell the Java SDK fully supports end to end is `(websockets, json)`.
- **Slice 3 (known incompatibilities and the client-results decision, D31/D32)** — three previously-prose-only incompatibilities became executable assertions (`KnownIncompatibilityTests`): `Context.GetHttpContext()` is always `null`; a custom `IUserIdProvider` silently diverges from the service's user index (demonstrated directly — a send to the real negotiated user id arrives, a send to the app-server-computed id from a deliberately divergent provider does not, within a bounded 2s wait); `.WithStatefulReconnect()` connects and works normally, falling back gracefully as ADR-005 already promised but never actually tested. **D32's decision, taken and implemented:** client results (`Clients.Client(id).InvokeAsync<T>(...)`) — a first-class SignalR feature since .NET 8, and finding 2's whole discovery: the framework's own `HubLifetimeManager<THub>.InvokeConnectionAsync`/`SetConnectionResultAsync` virtual members default to a bare `NotImplementedException` that doesn't even name Switchboard, and the Connector overrode neither. Declared a non-goal beside stateful reconnect (same structural reason: per-invocation state that can't survive the cluster-wide server-connection assignment, D18, unmodified — correctly routing the completion needs a new correlated-completion path, Phase-3-sized work, not a validation-phase fix) in [ADR-005](07-adr/ADR-005-protocol-compatibility.md) and [01-overview.md § Non-Goals](01-overview.md#non-goals), plus a Switchboard-specific `NotSupportedException` naming the limitation. `HubLifetimeManagerCoverageTests` reflection-pins the full split: all 13 abstract members of `HubLifetimeManager<THub>` overridden, the 3 virtual members each accounted for explicitly (`InvokeConnectionAsync`/`SetConnectionResultAsync` overridden to throw; `TryGetReturnType` deliberately left as the base implementation, since this Connector never creates a pending client-results invocation for it to have to answer about). New [04-design.md §14](04-design.md#14-hublifetimemanager-coverage-phase-5) records the coverage table. `MatrixDocumentWriter`/`MatrixDocumentGenerationTests` (**D36**) re-run the whole matrix against fresh real hosts and generate [docs/docs/11-compatibility-matrix.md](11-compatibility-matrix.md) — pass/not-applicable/untested only, a failing cell fails the test that generates the document before it can ever reach it as a fourth state.
- **Slice 4 (microbenchmarks, D33)** — `Keryhe.Switchboard.Benchmarks` (BenchmarkDotNet 0.15.8, `MemoryDiagnoser` on): envelope serialization round-trip, JSON/MessagePack frame parsing, `HubMessageClassifier.IsPing` (ping vs. non-ping, both protocols), `DefaultMessageRouter` fan-out at 1/100/1k/10k local targets using bounded `DropWrite`-mode fakes never drained (matching every real transport's channel configuration, so the curve reflects production behavior, not an idealized unbounded sink), and `ManagementInvocationWriter`'s argument mapping. **Real wiring conflict found and fixed, not anticipated by the plan's own finding 7 (which only verified BenchmarkDotNet against Core+Protocol):** `Keryhe.Switchboard.Server` pulls in `Microsoft.Orleans.Server` (needs `Microsoft.CodeAnalysis.Common >= 5.0.0`) while BenchmarkDotNet pulls in `Microsoft.CodeAnalysis.CSharp` 4.14.0 (needs exactly `4.14.0`) — an unresolvable transitive version conflict once the benchmarks needed `DefaultMessageRouter` (which lives in `Server`). Fixed with an explicit `Microsoft.CodeAnalysis.Common` 5.0.0 pin, which satisfies both ranges (one harmless `NU1608` informational warning remains). Verified with real `dotnet run -c Release` runs: fan-out scales roughly linearly, about 2ms and 2.4MB of allocation per additional 1,000 targets, no stalls at 10k — confirming `DropWrite` does what it's supposed to under this benchmark's synthetic load.
- **Slice 5 (load harness, observed limits, tuning guide, D33/D35)** — `Keryhe.Switchboard.LoadHarness`, a plain console app (BenchmarkDotNet's single-threaded microbenchmark loops cannot answer concurrent-load questions, per finding 7): `HostLimitsReport` (`ulimit -n`, macOS ephemeral port range via `sysctl net.inet.ip.portrange.first`/`.last`), `FailureClassifier` (ephemeral-port exhaustion, file-descriptor exhaustion, negotiate 503 — D5's correct backpressure, not a failure — handshake timeout, other), `ConnectionRamp` (real `HubConnection`s through the real negotiate redirect, bounded concurrency, stops early once a run of host-limit failures shows up rather than grinding through thousands more), `FanOutLoad` (one management-API broadcast to every ramped connection, harness-observed end-to-end latency), and `OtlpPercentileReader` (a throwaway `otel/opentelemetry-collector` container — Docker-gated exactly like the Java row — scraped via a Prometheus exporter for the service's own `signalr.message.outbound_duration`/`inbound_duration` histograms, D25, cross-checked against the harness's independent timings rather than re-deriving latency client-side). **A real 10,000-client run was performed, not simulated:** on the development machine (`ulimit -n` 10240, 16,384 ephemeral ports), the ramp reached **3,336** connections before stopping on 25 consecutive file-descriptor-exhaustion failures — correctly classified as a host limit, not a service defect, and reported precisely why (plan decision D35's core requirement).   **Two real bugs found by that milestone test, both silent-failure modes no earlier slice's tests happened to exercise, because every prior two-node test always gave both nodes at least one local app-server connection:**
  1. **`AddToGroup`/`RemoveFromGroup` didn't account for cluster-wide server-connection assignment (D18).** `RoutingServerEnvelopeDispatcher` mutated *this* node's `ILocalTransportRegistry` unconditionally for both envelope types, but once an app server's assigned client can live on a different node than the app server itself, the connection the envelope names is frequently not local — group membership silently never took effect on the node that actually needed it, so a client could join a room and never receive a single group message, no exception anywhere. **Fix:** `IBackplane.PublishAddToGroupAsync`/`PublishRemoveFromGroupAsync` mirror `PublishCloseConnectionAsync`'s existing owner-lookup-and-forward pattern (`IConnectionGrain.GetOwnerNodeAsync()` → `IHubGrain.AddToGroupCrossNodeAsync`/`RemoveFromGroupCrossNodeAsync` → `IHubObserver.OnAddToGroup`/`OnRemoveFromGroup`).
  2. **A node with live clients but zero local server connections for a hub never subscribed to that hub's grain at all.** `ObserverHeartbeatService` decided what to subscribe to purely from `IHubRegistry.GetAllHubs()` (server-connection-driven) — so a node serving only clients for a hub (exactly Slice 4's own "zero server connections" gate, and the ordinary few-hundred-millisecond window right after any node restart, before its own app-server pool has reconnected) had no observer subscribed anywhere. Every cross-node message meant for its clients — including a hub method invocation's own completion — was silently dropped with a logged warning and never delivered, hanging the client's `InvokeAsync` call forever. **Fix:** added `ILocalTransportRegistry.GetKnownHubNames()` (mirrors `IHubRegistry.GetAllHubs()`'s "sticks once seen" semantics) and `ObserverHeartbeatService` now subscribes to the union of both sources. Worth watching for: this is the second time a hub-name source got missed here — the first was `GetAllHubs()` itself needing a local server connection at all.

## Resolved 2026-07-26

**Connector inbound dispatch — designed ([04-design.md §11](04-design.md#11-connector--inbound-dispatch-synthetic-client-connections)).** The docs specified how the Connector *diverts* negotiate (§8) but never how an inbound `client_message` becomes a Hub method call. `IHubLifetimeManager` is outbound-only; everything inbound (`OnConnectedAsync`, argument binding, hub filters, per-method `[Authorize]`, streaming) lives in `HubConnectionHandler` → `DefaultHubDispatcher` and is unreachable without a `ConnectionContext`. Resolved with the mechanism the Azure SignalR SDK uses ([azure-signalr#13](https://github.com/Azure/azure-signalr/issues/13)): build a `ConnectionDelegate` via `ConnectionBuilder.UseConnectionHandler<HubConnectionHandler<THub>>()` and invoke it with a synthetic `ConnectionContext` backed by a `Pipe` pair. Decisions taken: `open_connection` carries `hubProtocol` (existing `[Key(5)]` field — no wire change) so the Connector can synthesize the mandatory handshake; identity is trusted from the envelope and attached via `IConnectionUserFeature`; rejection reuses `close_connection` with `error` rather than adding an ack round-trip. Applied to [03-protocol.md §2.3](03-protocol.md#23-message-envelope-format), [05-data-models.md](05-data-models.md), and [06-project-plan.md](06-project-plan.md) Phases 0–1.

**Class-level `[Authorize]` had a silent-drop hole — fixed in [04-design.md §8](04-design.md).** Verification against upstream source found that `MapHub<THub>()` copies hub-type attributes into *endpoint metadata*, so class-level `[Authorize]` is enforced by `AuthorizationMiddleware` on the HTTP request, while `DefaultHubDispatcher` enforces only *per-method* authorization and does no class-level check on connect. Because the client's transport request terminates at Switchboard and never reaches the app server, negotiate is the **only** surviving enforcement point — so a `MatcherPolicy` that swaps in a bare endpoint drops hub authorization with no error (the sample's `[Authorize] ChatHub` depends on it). §8 now requires the replacement endpoint to be built from the original's `Metadata`, and Phase 0 asserts it directly. (Sources: [HubEndpointRouteBuilderExtensions.cs](https://github.com/dotnet/aspnetcore/blob/main/src/SignalR/server/SignalR/src/HubEndpointRouteBuilderExtensions.cs), [DefaultHubDispatcher.cs](https://github.com/dotnet/aspnetcore/blob/main/src/SignalR/server/Core/src/Internal/DefaultHubDispatcher.cs).)

**`Context.UserIdentifier` vs. the service's user index — reconciled.** `UserIdentifier` is computed by `IUserIdProvider` (default: `ClaimTypes.NameIdentifier`), while the service routes `send_to_user` on the `userId` captured at negotiate; divergence would break `Clients.User(...)` silently. The Connector now synthesizes `NameIdentifier` from the envelope `userId`. A custom `IUserIdProvider` remains a documented hazard (risk register) that must be mirrored in the app server's forwarded negotiate.

**Phase 0 spike scope widened.** Previously covered negotiate interception only. It now also proves inbound dispatch — the other unproven Connector mechanism — plus the `[Authorize]` metadata assertion. Renamed *Connector Mechanism Spike*.

### Medium — resolved

**Management API auth — decided: a separate management token.** [ADR-004](07-adr/ADR-004-token-authority.md)'s position wins over the "server access token **or** …" alternative that [03-protocol.md Part 3](03-protocol.md#part-3-management-rest-api) previously allowed: an app server token must not be able to drive the management API. Part 3 now specifies the management token's required claims (`role: management`, `aud` = `ManagementAudience`) and its CLI generation; `ManagementSigningKey` / `ManagementSigningKeyFallback` / `ManagementAudience` added to `SwitchboardOptions` ([05-data-models.md](05-data-models.md)); `GET /api/v1/health` corrected from "server or management token" to management only; ADR-004 gained a three-token summary table; Phase 4 deliverable updated.

**Pattern A — specified, and its flow corrected.** Writing it up exposed a latent contradiction: a *non-redirect* negotiate response has no field able to carry an access token, so Pattern A as drafted could not authenticate its own transport upgrade. Resolved by having service-direct negotiate **return a redirect to itself**, reusing Pattern B's entire token-issuance and Accept-Phase path rather than introducing a second transport-auth mode with `connectionToken` as a bearer secret. Identity comes from `X-Switchboard-UserId` / `X-Switchboard-Claims`, governed by four mandatory security rules (disabled by default; fail-fast startup when enabled with an empty allowlist; headers stripped for non-allowlisted peers; match on the immediate peer, not `X-Forwarded-For`). **Backpressure default — decided: `DropWrite`.** `WriteChannelFullMode` default flipped from `BoundedChannelFullMode.Wait`, which contradicted the non-blocking fan-out described in [02-architecture.md](02-architecture.md) and [04-design.md §5](04-design.md). A slow client now sheds messages instead of stalling broadcast fan-out for every other client.

**Phase 3 group membership — clarified.** `IGroupGrain` is the single source of truth under clustering; `InMemoryConnectionRegistry` is not in play (`OrleansConnectionRegistry` replaces it wholesale, per [ADR-002](07-adr/ADR-002-connection-registry.md)). The per-node `connectionId → groupNames` map is a **node-local cache** living beside the transport handles in `ILocalTransportRegistry`, used only to avoid a cross-grain scan on disconnect — never for routing or membership queries.

**Stateful reconnect — decided: deferred / not supported.** Keeps fire-and-forget as a non-goal. Stateful reconnect (`.withStatefulReconnect()`, .NET 8+) buffers un-acked messages for replay on resume — the replay the overview already excludes, and costly in a proxy/clustered topology (per-connection buffers; owner-node-bound state).
